PROPOSAL

Orient in 60 seconds

What changes when successful EMR integration is assumed?

Architecture response: add in-context launch, read-through source artifacts, clinician-confirmed facts, a human criterion worksheet, bounded packet manifests, tumour-board handoff, and transactional EMR write-back. Do not use EMR data to rank trials or compute eligibility.
1

Primary workflow

Clinician selects a trial, reviews EMR evidence, records criterion judgements, authorises a packet, and hands work to a coordinator/site.

2

Systems of record

EMR owns clinical artifacts and human clinical record. Registries own registry facts. Trial Relay owns operational assertions, tasks, and audit.

3

Data posture

Read clinical content on demand. Persist references, human review states, packet manifest, task state, and audit—not copied clinical documents by default.

4

Simplest shape

Browser app launched by EMR, one modular server application, one transactional store, permissioned registry and EMR adapters.

Five risks

  1. Integration can increase available evidence while accidentally implying automated matching.
  2. EMR write-back can create duplicate or conflicting clinical/operational records without clear ownership.
  3. Clinical content, patient references, and launch credentials cross a new trust boundary.
  4. Source rights and site-verification operations remain unresolved even with perfect EMR integration.
  5. Feature breadth can hide the primary test: whether authoritative site verification and closed-loop handoff create material value.

DYNAMIC VIEW

EMR-to-human-review-to-write-back

How does the critical P0 path execute without letting the system make a clinical judgement?

Success trace: each clinical statement remains source-linked; every judgement/release is a named human action; the EMR remains the clinical system of record.

Important failure trace

  • Launch invalid/expired → deny case workspace; allow general registry workspace only.
  • Artifact missing/unreadable → show information gap; never synthesize a substitute.
  • Conflicting source assertions → display both and require clinician resolution.
  • Packet changed after approval → invalidate approval and require re-review.
  • EMR version conflict → retain local draft, show diff, require human reconcile; do not retry a write blindly.
DATA FRESHNESS FLOW

Registry and site verification remain independent

Does EMR integration solve the original freshness problem? No.

Registry lifecycle

rights_approved → fetched → validated → normalized → published → stale/superseded

Rights/schema/parse failures quarantine the source version and preserve the last valid permitted snapshot.

Site assertion lifecycle

not_checked → attempted → verified | no_response | discrepancy → expired

Only an authorised human/site source creates the assertion. Expiry returns work to the queue.

Critical separation: clinician-confirmed patient facts, registry trial facts, and site operational assertions have different owners and cannot be merged into one “match confidence” score.

Retry contract

  • Retry only permitted idempotent reads for transient failures within a configured time/attempt budget.
  • Do not retry rights denials, schema incompatibility, invalid signatures, or CAPTCHA.
  • Human contact attempts are workflow events, not automated network retries.
  • Source outage degrades to explicit stale state; verification and EMR tasks continue independently.

RELIABILITY AND OBSERVABILITY

Degrade by capability, never by truth

What stays available when one dependency fails?

EMR unavailable

Disable case artifacts, confirmations, packet changes and write-back. Keep general registry search, site verification and non-patient operations available. Never use cached clinical content unless explicitly approved.

Registry unavailable

Serve only permitted last snapshot with visible stale age. Keep case workspace, site assertions and task handoff available. Do not label anything “live.”

Site channel unavailable

Record attempts and no-response. Do not infer closed/open status. Continue registry/EMR work and escalate only through approved policy.

Recovery

  • Transactional backups cover Trial Relay operational state and audit; clinical sources remain recoverable through EMR ownership.
  • Restore must preserve assertion/task/audit referential integrity and mark external sessions invalid.
  • RTO, RPO, backup frequency, retention and drill cadence require owner/institution targets; do not invent them.
  • Roll back application and adapter independently at the release level, but schema changes must remain backward compatible or have tested restore.

Alert fatigue controls

  • Group repeated source changes by trial and verification task.
  • Send immediate alerts only for approved events; digest lower-priority changes.
  • Stop alerts when the follower leaves, task closes, access is revoked, or trial reaches the rule's stop state.
  • Measure unread age, duplicate suppression, unsubscribe rate, delivery failures, and action completion—not message volume.
ARCHITECTURE DECISION

Keep alerts inside the same application first

Do alerts require a new service or message broker? Not at the current unknown scale.

Write path

  1. Commit the source, verification, packet, board, trial-team, or task change.
  2. In the same transaction, append one alert event with a stable fingerprint.
  3. Create allowed recipient/channel delivery rows from active subscriptions.

A state change cannot commit without its alert event when the rule requires one.

Delivery worker

  1. An in-process scheduled worker claims due delivery rows.
  2. It sends through in-app, EMR inbox/Task, or separately approved email adapters.
  3. It records success, permanent failure, next safe retry, read/ownership, and close.

No external queue is required until measured load or isolation demands it.

Retry rule: retry only transient, idempotent delivery failures within a time/attempt budget. Do not retry permission denial, revoked access, invalid recipient, unsafe content, or permanent template error.
