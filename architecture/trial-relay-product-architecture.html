Trial Relay product and system architecture

A design for validating the recommended site-verified operations layer: general trial discovery, source provenance, time-bounded human verification, and a closed-loop inquiry task. Patient-specific matching remains outside the boundary.

PROPOSAL

Orient in 60 seconds

What are we building, for whom, and where is the hard boundary?

Recommended transition: validate a manually operated, source-linked trial and site-verification workflow before selecting a production stack. If value and data rights pass, evolve to one modular application and one transactional data store—not microservices.
1

Primary user

Clinical research coordinator; treating oncologist is the search/inquiry initiator. Site steward supplies operational assertions.

2

Primary job

Get an authoritative recent site answer and keep the inquiry owner and acknowledgement visible.

3

Core invariant

Registry fact, normalized value, and site assertion are separate records with separate owners and dates.

4

Excluded

No patient data, eligibility inference, trial ranking, treatment recommendation, or autonomous patient communication.

Five decisions and risks to remember

  1. CTRI has no supported public programmatic contract found; written access and reuse terms are a gate.
  2. The verification operation—not the search UI—is the likely differentiator, cost centre, and failure point.
  3. Human site assertions expire; “no response” never means “not recruiting.”
  4. A general information tool and a patient-specific matcher are different regulated/safety products.
  5. P0 proves workflow value; P1 makes it operable; P2 scales only after buyer, rights, and unit economics exist.

PRODUCT CONTRACT

P0, P1, and P2 capability order

What must be learned or made operable before later capabilities are justified?

P0 — prove the job

Bounded pilot

  • General trial search
  • Exact source provenance
  • Registry/site dual status
  • Human verification and expiry
  • Human-approved inquiry lifecycle
  • Audit events and patient-input boundary
  • Loading, empty, stale, conflict, and no-response states
P1 — operate reliably

Only after repeated P0 use

  • Declared-ID cross-registry review
  • Source health and schema-change handling
  • Saved operational views
  • Bulk work assignment—not bulk state mutation
  • Institution roles and permissions
  • Approved inquiry templates
P2 — scale proven operations

Buyer and economics required

  • Authorised site self-service
  • Aggregate operations analytics
  • Approved institutional export
  • Evidence-led multilingual copy
  • Network/tenant governance
  • Verification capacity and cost controls
Not P2: patient-note ingestion, biomarker interpretation, eligibility scoring, trial ranking, treatment recommendations, or autonomous patient messaging. These require a different product decision and safety programme.

C4 — CONDITIONAL CONTAINER VIEW

Simplest target if P0 passes

Which runnable responsibilities require independent boundaries? None yet justify independent services.

Question answered: what is the fewest deployable/stateful boundaries that satisfy P0 correctness? Browser + one modular application + one transactional store. A scheduled job can run inside the application; no queue or cache is justified yet.

Module invariants

  • Source processing never calls an unapproved endpoint.
  • Search reads published normalized rows and source provenance; it cannot access patient data because none exists.
  • Verification and task commands transact state change and audit event together.
  • Only the source-processing module writes source snapshots; only verification writes site assertions; only task workflow changes task state.
DYNAMIC VIEW

Success path and failure recovery

How does a permitted source fact become a human-owned inquiry without becoming an eligibility judgement?

Question answered: where do validation, synchronous work, durable side effects, human decisions, and recovery occur? No asynchronous broker is required; a bounded scheduled job plus durable job status is enough until measured load proves otherwise.

Retry ownership

  • Retry only permitted idempotent source reads for transient timeouts/5xx, within a configured attempt/time budget.
  • Do not retry authorization failures, schema incompatibility, invalid signatures, CAPTCHA, or explicit rate-limit bans without human disposition.
  • Verification attempts are human workflow events, not automated network retries.
  • Task commands use idempotency keys so a repeated client request does not create duplicate transitions or audit events.

Independent state machines

Source record

discovered → rights_approved → fetched → validated → published → stale/superseded

Any rights/schema failure goes to quarantined.

Site assertion

not_checked → attempted → verified | no_response | discrepancy → expired

Expiry returns work to the queue without deleting history.

Inquiry task

draft → approved → sent → acknowledged → closed

unable_to_contact is terminal; there is no eligibility state.

CONTRACTS

Commands, errors, and consistency

Which semantics prevent silent data corruption and misleading freshness?

Source ingestion contract

  • Inputs: approved source ID, permitted method, schema version, retrieval context.
  • Identity: source + source record ID + source version/hash.
  • Success: immutable snapshot, validated projection, diff, job result.
  • Errors: rights denied, unauthorized, rate limited, unavailable, malformed, schema incompatible, identity uncertain.
  • Compatibility: new source fields ignored only when safe; missing required field quarantines record/batch.

Verification command

  • Authenticated user with verification role and institution scope.
  • Inputs: site, assertion enum, source role, authority confirmation, method, evidence reference, observed time, expiry policy, reason.
  • Concurrency: expected current assertion version; stale write returns conflict.
  • Transaction: assertion and audit event commit together.
  • Validation: no patient payload; no assertion inferred from silence.

Inquiry transition command

  • Inputs: task ID, expected state/version, requested next state, actor, reason, idempotency key.
  • Only allowed transition edges succeed.
  • Repeated idempotency key returns original result.
  • Task state and audit event commit atomically.
  • External sending remains human-approved and institution-authorised.

General search contract

  • Inputs limited to general trial attributes.
  • Response includes source provenance, state type, observed time, age, and stale/conflict markers.
  • Never returns match score, eligibility status, or recommendation ordering.
  • Unavailable source does not make the whole search fail if a valid stale snapshot is permitted; stale state is explicit.
Consistency choice: strong transactional consistency within assertion/task/audit writes. Eventual freshness from external registries is unavoidable and must be visible rather than hidden behind a “live” label.

Assets and trust boundaries

  • Assets: source permissions/credentials, site contact routes, assertions, task ownership, audit evidence, and product trust.
  • External registry and site content is untrusted until validated for display and authority.
  • Privileged actions: approve source, link uncertain identity, record site assertion, advance task, change expiry/policy, export audit.
  • Secrets must not appear in browser bundles, source snapshots, logs, analytics, or screenshots.

Which signals show whether the system is useful, safe, and maintainable?

User journey signals

  • Time from search/inquiry to authoritative response
  • Inquiry acknowledgement and human closure
  • Searches ending without actionable contact
  • Coordinator person-minutes per resolved inquiry

Freshness signals

  • Assertions within expiry window
  • Expired queue age
  • Registry/site discrepancy rate
  • Source-to-published lag and stale views

Integrity signals

  • Quarantined batches/records
  • Schema incompatibility
  • Uncertain identity links
  • Rejected stale writes and invalid task transitions

Cost model
