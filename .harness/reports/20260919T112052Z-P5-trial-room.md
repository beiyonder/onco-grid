# Work report — P5 C2 Trial room

## Problem

The accepted trial profile exposed Follow and a general-inquiry dialog but did not provide the blueprint's contextual Trial room: pinned source facts, verified participant roles, question categories, official-response authority, or explicit resolution paths. The sticky profile could also grow taller than the viewport, leaving lower content unreachable, and the proposed participant class initially collided with the existing tumour-board avatar class.

## Decision

Deliver Phase 1 slice 3 on `feat/trial-room` as a browser-session workflow. Add Trial room as the third profile section; keep source/status/site pins immutable from discussion; let users post only general operational questions after affirming that no patient information is present; show treating oncologist, research coordinator, and verified site coordinator roles; permit only the synthetic verified site role to record an official response or source correction. Allow human outcomes for official answer, informal answer, draft action with owner/due date, proposed source correction, unresolved, or outdated. Never mutate registry or verification pins from discussion. Make long desktop profiles independently scrollable while keeping the full document flow on narrow screens, and namespace Trial room participant styles.

## Evidence

- Follow state — Follow trial set `aria-pressed=true`, changed the label to `Following trial`, updated the pinned room state, and caused later resolved-thread events to enter Inbox without changing registry or site-confirmation pins.
- Room shell — the selected trial exposed four immutable pins (registry source/ID, registry status/date, independent site state, retained India-site count), three scoped participants with role and institution, an official-response boundary, related-handoff count, and a clearly labelled browser-session reset boundary.
- Question posting — a coordinator posted a Site status question only after checking `No patient-identifying or patient-specific information`; the thread became `Awaiting confirmation`, named author/role/date, received focus, and left registry/site states unchanged.
- Authority failure — attempting `Official site response` as the coordinator was blocked, retained the awaiting state, returned focus to the outcome selector, and displayed `Only the verified site role can record an official response or source correction.`
- Official response — after switching to the synthetic verified site coordinator, the thread resolved as `Official site response`, recorded the source role/date, produced a followed-trial Inbox update, and still left registry `Recruiting` and independent site state `Not independently site-verified` unchanged.
- Action outcome — a separate coordinator thread resolved to `Action created`; it created draft `INQ-1045` with owner `A. Rao`, due date 20 Sept 2026, route `Trial room`, linked trial, visible action ID, and related-handoff count `1`.
- Correction outcome — the verified site role recorded `Source correction proposed`; the UI and toast stated that the registry source was unchanged, and the registry assertion remained `Recruiting`.
- Unresolved outcome — a coordinator recorded `No authoritative response has been received`; the thread remained `Unresolved`, retained its resolution form for later authoritative closure, and did not turn silence into a negative site state.
- Overflow and style isolation — at `1440×1000`, the 894 px profile viewport scrolled 1,451 px of room content internally; the composer became reachable by normal scrolling. At `390×844`, the profile returned to document flow, room/pins/forms flattened to one column, and page-level `scrollWidth` equalled `clientWidth` at 390. Trial room rendered exactly three `room-participant` entries while the tumour-board's five existing participant avatars retained their original classes and styles.
- Final desktop task flow produced zero console warnings, console errors, or page errors.
- Reduced-motion emulation set transition duration to `0.00001s` and document scroll behavior to `auto`.
- `node --check web/app.js`, `git diff --check`, `python3 research/validate_ledger.py` (70 records), and `python3 scripts/fetch_india_oncology_trials.py --validate-only` (285 records) passed.

## Risks and gaps

Trial room data, role switches, follow state, messages, tasks, and alerts are browser-memory validation behavior and reset on reload. The synthetic role switch demonstrates the authority boundary but is not production identity or authorization. No external message is sent, no real site participant is contacted, and no registry or site verification record is changed. Thread notes rely on the explicit no-patient-data boundary rather than a production data-loss-prevention control. Unified Inbox consolidation is the next phase. P5 validation and product lock remain open.
