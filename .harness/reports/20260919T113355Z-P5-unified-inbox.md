# Work report — P5 C2 Unified Inbox

## Problem

The accepted shell labelled Updates, Messages, and Tasks as Inbox groups, but Messages and Tasks still navigated to separate global-style views and only Updates rendered inside Inbox. Alert rows did not consistently name context, owner, due state, and source. Trial room outcomes, generated alerts, inquiries, and verification work could represent the same underlying event in more than one queue.

## Decision

Deliver Phase 2 slice 1 on `feat/unified-inbox`. Normalize alerts, Trial room threads, inquiries, and verification work into one browser-session Inbox model with exactly one classification per item: Updates for source/workflow changes, Messages for human responses/conversation state, and Tasks for owned next steps. Render each classification through one stream component with context, owner, due state, source, read state, and a source-context action. Suppress generated Trial room alerts when the canonical thread exists, suppress acknowledged inquiry rows when a canonical acknowledgement alert exists, and represent task-resolved threads only through their generated inquiry. Keep the existing detailed verification and handoff workspaces as contextual destinations rather than global queues.

## Evidence

- Initial normalized state after loading 285 registry records — Updates `2`, Messages `2`, Tasks `286`; Inbox navigation badge `3` unread. Updates and Messages rendered all items; Tasks rendered the first 60 and stated that 226 more remained in the attached work contexts.
- Row contract — each inspected row contained a title/body, exact context, named owner, due state, and source. The first Update linked `NCT07216703 · Visakhapatnam`, named treating oncologist and research coordinator, stated no deadline, and named the ClinicalTrials.gov snapshot. The first Task linked `INQ-1042 · NCT07216703`, named A. Rao, showed `Overdue · 14 Sept 2026`, and named the site trial office human-workflow source.
- Read-state isolation — marking visible Updates read changed Inbox unread count from 3 to 1 without clearing the unread Message. Marking visible Messages then reduced the nav count to 0. Tasks had no unread items and correctly disabled the read action.
- Canonical classification — the acknowledged `INQ-1038` appeared once through its handoff Message; the sent `INQ-1042` appeared once as an owned Task; the seeded site-verification alert was suppressed because the same trial already had a verification Task.
- Dynamic Trial room deduplication — resolving a followed Trial room thread as an official response increased Messages from 2 to 3, produced exactly one `thread:` row, produced zero generated `Trial room:` alert rows, and named `Verified site coordinator · Trial room` as its source.
- Context routing — the first handoff Task opened Referral and inquiry handoffs; a verification Task opened Verification queue with `selectedVerificationId` matching the Inbox record; the Trial room Message opened the exact trial, Room tab, and thread with focus while setting the exact trial search context.
- Desktop at `1440×1000` — one dense stream plus quiet context rail, no page-level horizontal overflow. Narrow mobile at `390×844` — three Inbox tabs fit without overflow; stream, accountability facts, and actions flattened to one column; `scrollWidth = clientWidth = 390`.
- Reduced-motion emulation set transition duration to `0.00001s` and document scroll behavior to `auto`.
- Final 60-task render produced zero console warnings, console errors, or page errors.
- `node --check web/app.js`, `git diff --check`, `python3 research/validate_ledger.py` (70 records), and `python3 scripts/fetch_india_oncology_trials.py --validate-only` (285 records) passed.

## Risks and gaps

The 285 real records all lack independent site confirmation and therefore create a large unscheduled verification queue; the 60-row cap prevents rendering overload but assignment and saved-view strategy require user validation. Classification is deterministic browser-memory logic, not a persisted event model. Context actions currently navigate to the attached workspace; inline resolution and origin-focus return belong to the next slice. Notification rules and external channel policy remain unchanged. P5 validation and product lock remain open.
